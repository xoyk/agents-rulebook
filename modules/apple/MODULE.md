## An Apple app: nothing is clicked into the project

The Xcode project is generated — by XcodeGen from `project.yml`, by Tuist, by
Expo's prebuild — and is not the source of anything. Whatever is set by
clicking in Xcode's project settings lives only until the next generation,
which throws it away without a word. So every setting goes into what the
generator reads, and nothing is ever fixed by hand in the generated project.

Signing is the setting this bites first, because it is personal: the Team is
the one value a project needs that is not the same for everyone who builds it.
It lives in a file of its own that the generated project includes and git
ignores:

```text
{{path of the committed config, e.g. ios/Config/Base.xcconfig}}   committed:  #include? "Signing.local.xcconfig"
{{path of the local file, e.g. ios/Config/Signing.local.xcconfig}}   ignored:    DEVELOPMENT_TEAM = <team id>
{{…/Signing.local.xcconfig.example}}   committed:  the same, with the id blanked
```

`#include?` is optional, so a clone without the local file still builds for the
simulator; only a device build needs the Team. An Expo project has no xcconfig
to include into: its Team is `ios.appleTeamId` in `app.json`, which prebuild
writes into the project it generates.

On 2026-09-28 the Team in one project's Signing tab reset to None every time
the user set it. The project was generated by XcodeGen, and the agent ran
`xcodegen generate` before every test run — each run erased the choice the
user had just made.

<!-- rule:apple-team -->
### The Team is found, not asked for twice

A person has one Apple Developer Team and uses it in every project, so the
Team ID is kept once per machine, next to the rulebook's registry, and a
project gets a copy in its local signing file:

```json
// ~/.config/agents-rulebook/apple.json
{ "teamId": "<10 characters>" }
```

`install.mjs` looks there first. When it is empty, it looks through the other
projects in the registry — a `DEVELOPMENT_TEAM` in an xcconfig or a project
file, an `appleTeamId` in an Expo `app.json` — and offers what it finds,
naming the project it came from, for the user to confirm with
`install.mjs --apple-team <id>`. It never picks one silently: two teams on one
machine is ordinary for anyone who also works for somebody else.

The Team ID is not a secret — it is printed in every signed app — but it stays
out of the repository all the same: a clone by someone else signs with their
Team, and a public repository has no reason to name the owner's.

On 2026-09-28 the Team for a new project was taken from another project on the
same machine in one search, and the user asked for the install to do that
search itself.

<!-- rule:apple-simulator -->
### A simulator destination names its OS

```bash
-destination 'platform=iOS Simulator,name={{phone}},OS={{version}}'
```

A machine usually carries the same phone on several iOS runtimes, and
`name=` alone does not pick one: on 2026-09-27 a bare `name=iPhone 16` made
`xcodebuild` fall back to "My Mac" and fail. The check command in this file
names both, and so does any command written into a script or a hook.

<!-- rule:apple-device -->
### The first run on a device is the user's

A build for a device signs with the user's Team, and the first one creates
provisioning profiles and registers the device in their Apple Developer
account. That is the account's business, so the agent builds and tests on the
simulator and hands the device run to the user: it does not start one, even
with the Team already in place. Testing on the phone is where the user
accepts a build, and it belongs in `Needed from you`.
